# 0장 실측 결과 (기획서 "착수 전 측정")

측정일: 2026-09-14 / 대상: docker `atlassian/confluence:7.8.1` + PostgreSQL 11
측정 방법: `tools/make-testdata.py` 로 픽스처를 만든 뒤 REST · psql · `javap`(confluence 7.8.1 jar)

기획서 0장의 원칙대로 **실측이 문서를 이긴다.** 아래에서 기획서와 다른 항목은 실측값을 쓴다.

## [V1] 첨부 메타데이터의 저장 위치 — 기획서 기대와 다르다

첨부는 `CONTENT` 테이블에 `CONTENTTYPE='ATTACHMENT'` 행으로 들어간다(기획서 맞음).
**버전 체인은 기획서가 상상한 연결 리스트가 아니다.**

```
 contentid | title     | version | prevver | content_status | pageid  | spaceid
 3670085   | spec.xlsx |       4 |  (null) | current        | 3670084 | 4194305
 3670086   | spec.xlsx |       1 | 3670085 | current        | 3670084 | 4194305
 3670087   | spec.xlsx |       2 | 3670085 | current        | 3670084 | 4194305
 3670088   | spec.xlsx |       3 | 3670085 | current        | 3670084 | 4194305
```

- **최신 버전 = `PREVVER IS NULL` 인 행이다.** 구버전 행이 전부 *머리(head)* 를 가리킨다.
  이전 버전을 가리키는 것이 아니다 — 체인을 거슬러 올라가는 코드를 쓰면 안 된다.
- 구버전 행도 `CONTENT_STATUS='current'` 다. **상태만 보면 구버전이 현재 첨부로 세진다.**
  이 인스턴스에서 `ATTACHMENT` 행 47개 중 실제 첨부는 44개였다(구버전 3개).
- 같은 모델이 `PAGE` · `SPACEDESCRIPTION` 에도 그대로 적용된다. 페이지 88행 중 현재
  페이지는 39개고 49개가 과거 버전이었다. **본문 스캔에서 이 구분을 빼면 과거 본문을
  현재 본문으로 읽는다**(5장 "이력 참조" 판정이 통째로 무너진다).
- 크기·타입은 `CONTENTPROPERTIES` 에 있다. 기획서의 추측(FILESIZE/MEDIA_TYPE)이 맞다.
  - `FILESIZE` → **`LONGVAL`**
  - `MEDIA_TYPE` → **`STRINGVAL`**
  - 그 밖에 `HIDDEN`, `MINOR_EDIT` (둘 다 longval)
  - 구버전 행도 각자 `FILESIZE` 를 갖는다 → **구버전 용량 집계가 가능하다.**

## [V2] 디스크 배치 — 파일시스템은 건드리지 않는다

```
<confluence-home>/attachments/ver003/<hash>/<...>/<spaceid>/<...>/<pageid>/<첨부id>/<버전번호>
<confluence-home>/attachments/ver003/nonspaced/.../<첨부id>/<버전번호>
```

- 기획서의 `ver003` 추측이 맞다.
- **모든 버전이 머리 첨부 id 디렉터리 아래 "버전번호" 파일명으로 모여 있다.** 구버전
  행의 contentid 로는 디렉터리가 만들어지지 않는다.
- 디스크 파일 크기가 `FILESIZE` 와 정확히 일치했다(4096/8192/12288/16384).
  → **DB 메타만으로 용량을 집계해도 된다. 파일시스템은 읽지 않는다**(권한·경로 문제 회피).
- 단 `<버전번호>.extracted_text` 사이드카가 별도로 존재하고 `FILESIZE` 에 안 들어간다.
  즉 우리 수치는 "첨부 본체 합계"이고 홈 디렉터리 전체 용량보다 작다. 화면에 명시한다.
- `nonspaced/` 가 실재한다 → **스페이스가 없는 첨부가 있다**(V6 참조).

## [V3] Java API 로 어디까지 되는가 — 스페이스 단위 순회는 없다

`javap` 로 확인한 7.8.1 API:

- `AttachmentManager` 에 **스페이스 단위 조회가 없다.** 전부
  `ContentEntityObject`(페이지/블로그) 단위다. 기획서가 걱정한 대로다.
- 대신 `attachmentManager.getAttachmentDao()` 로 내려가면 두 개가 있다.
  - `findLatestVersionsIterator()` — **인스턴스 전체 최신 버전 첨부를 스트리밍**한다.
    페이지를 다 돌 필요가 없다. 이 앱의 스캔은 이걸 한 번 돌리는 것으로 시작한다.
  - `findAll()` — 구버전 포함 전부를 `List` 로 준다. 메모리 위험이 있어 쓰지 않는다.
- 구버전은 `AttachmentManager#getPreviousVersions(Attachment)` 로 얻는다. 첨부당 1회
  조회다. **`getVersion() > 1` 인 첨부에만 호출하면** 대부분의 첨부(버전 1개)는
  추가 조회가 0회다.
- `getAttachmentStatistics()` 는 `AttachmentStatisticsDTO(전체 수, 현재 수)` 뿐이다.
  용량이 없다 → 랭킹에 쓸 수 없다.
- `Attachment` 에서 바로 나오는 것: `getFileSize()`, `getFileName()`, `getMediaType()`,
  `getSpace()`, `getContainer()`, `getVersion()`, `getLastModificationDate()`.
  **컨테이너 종류를 `getContainer().getType()` 으로 받으므로 컨테이너 종류를 열거하지
  않아도 된다** — V6 의 목록이 늘어나도 코드가 안 바뀐다.

## [V4] 읽기 전용 SQL — 필요 없다

V3 의 `findLatestVersionsIterator()` 가 있으므로 **직접 SQL 경로를 v1 에 넣지 않는다.**
근거:

- `confluence.cfg.xml` 이 JNDI 가 아니라 직접 JDBC URL 을 쓴다 → 기획서가 적은
  JNDI DataSource 경로는 이 환경에 존재하지 않는다.
- `SessionFactory` 를 `@ComponentImport` 로 받는 경로는 OSGi 해석이 실패하면 **앱 자체가
  기동하지 않는다.** 스페이스 랭킹 하나 때문에 그 위험을 지지 않는다.
- 직접 SQL 은 두 DB 방언(PostgreSQL/H2/Oracle/MSSQL)을 우리가 책임진다는 뜻이기도 하다.

집계 자체가 가능하다는 것은 psql 로 확인했다(아래). 앱은 같은 값을 API 로 만든다.

```sql
SELECT COALESCE(s.spacekey,'(no space)'), COUNT(*) FILTER (WHERE a.prevver IS NULL),
       SUM(p.longval), SUM(p.longval) FILTER (WHERE a.prevver IS NOT NULL)
FROM content a
JOIN contentproperties p ON p.contentid=a.contentid AND p.propertyname='FILESIZE'
LEFT JOIN spaces s ON s.spaceid=a.spaceid
WHERE a.contenttype='ATTACHMENT' AND a.content_status='current'
GROUP BY 1;
```

이 쿼리는 **교차 확인용**으로 남긴다(앱 수치와 DB 수치가 같아야 한다).

## [V5] 첨부를 참조하는 본문 문법 — 추측하지 않고 Confluence 에게 물었다

`POST /rest/api/contentbody/convert/storage` 에 wiki 표기를 넣어 저장 형식을 받았다.
(7.8.1 에 이 엔드포인트가 있다는 것도 여기서 확인했다.)

| 입력(wiki) | 저장 형식 |
|---|---|
| `!a.png!` | `<ac:image><ri:attachment ri:filename="a.png"/></ac:image>` |
| `[^a.pdf]` | `<ac:link><ri:attachment ri:filename="a.pdf"/></ac:link>` |
| `{viewfile:name=a.xlsx}` | `<ac:structured-macro ac:name="viewfile"><ac:parameter ac:name="name"><ri:attachment ri:filename="a.xlsx"/></ac:parameter></ac:structured-macro>` |
| `{multimedia:name=v.mp4}` | 위와 같은 모양(`ac:name="multimedia"`) |
| `{viewpdf:name=a.pdf}` | 위와 같은 모양(`ac:name="viewpdf"`) |
| `{gallery:include=a.png,b.png}` | `<ac:parameter ac:name="include">a.png,b.png</ac:parameter>` — **문자열이다** |
| `!AJA:cross^shared.png!` | `<ri:attachment ri:filename="shared.png"><ri:page ri:space-key="AJA" ri:content-title="cross"/></ri:attachment>` |

**설계 결론.**

1. **`ri:attachment` 엘리먼트를 트리 어디서든 전부 걷는다.** 매크로 이름을 열거하지
   않는다. `viewfile` / `multimedia` / `viewpdf` / `viewdoc` … 는 전부 같은 모양이고,
   우리가 모르는 매크로도 같은 엘리먼트를 쓴다. 기획서가 매크로를 하나씩 나열한 것은
   불필요할 뿐 아니라 빠뜨리는 쪽으로 틀린다.
2. **예외는 `gallery` 뿐이다.** `include` / `exclude` 가 평문 문자열이라 엘리먼트 순회로는
   안 잡힌다. 이 매크로만 파라미터를 콤마로 쪼갠다.
3. **`ri:page` 자식이 있으면 교차 참조**다. 같은 스페이스면 `ri:space-key` 가 붙지 않는
   경우가 있으므로 **없을 때는 참조하는 본문의 스페이스로 해석**한다.
4. `ri:page` 자식이 없으면 자기 페이지의 첨부다.

## [V6] 첨부가 페이지 밖에 붙는 경우 — 있다

이 인스턴스의 첨부 컨테이너 분포:

| 첨부 상태 | 컨테이너 타입 | 컨테이너 상태 | 수 | spaceid 없음 |
|---|---|---|---|---|
| current | PAGE | current | 40 | 0 |
| current | PAGE | **draft** | 5 | 0 |
| current | BLOGPOST | current | 1 | 0 |
| current | **USERINFO** | current | 1 | **1** |
| deleted | PAGE | deleted | 1 | 0 |

- **`USERINFO` 컨테이너의 첨부(프로필 사진)는 `SPACEID` 가 없다.** 디스크에서도
  `ver003/nonspaced/` 아래에 있다.
  → **랭킹 화면의 스페이스 합계와 인스턴스 총계가 일치하지 않는다.** "(스페이스 없음)"
  행을 따로 두고, 그 행은 스캔·정리 대상이 아니라는 것을 화면에 적는다.
- **초안(draft) 페이지에도 첨부가 붙어 있다.** 초안 본문은 사용자가 저장하지 않은
  상태이고 다른 사람에게 보이지 않는다. 이 첨부를 "고아"로 찍으면 안 된다 —
  별도 컨테이너 상태로 취급한다.
- `SpaceDescription` 은 `ContentEntityObject` 이고 `getAttachmentUrlPath(Attachment)` 를
  갖는다 → **스페이스 로고는 SPACEDESCRIPTION 컨테이너의 첨부다.** 이 인스턴스에는
  로고를 설정한 스페이스가 없어 행으로 확인하지는 못했다(미실측으로 표기).
- `pagetemplates` 테이블은 **행이 0개**다. 본문이 `content`/`bodycontent` 가 아니라
  `pagetemplates.content` 에 따로 있으므로, 템플릿을 스캔에 넣으려면 별도 경로가 필요하다.
  v1 은 넣지 않고 한계로 명시한다.
- **컨테이너 종류를 코드에 열거하지 않는다.** `getContainer().getType()` 을 그대로 쓰고,
  모르는 타입은 "기타 컨테이너"로 묶는다. 위 표는 이 인스턴스의 스냅샷일 뿐이다.

## [V7] 휴지통 — 기획서의 라벨 하나로는 부족하다

두 가지 다른 일이 **같은 컬럼 값**으로 나타난다.

| 한 일 | 첨부 행 | 컨테이너 행 |
|---|---|---|
| 페이지를 휴지통에 넣음 | `content_status='deleted'` | `content_status='deleted'` |
| 첨부 하나만 삭제(`DELETE /rest/api/content/{id}`) | `content_status='deleted'` | `current` 그대로 |

- 즉 **첨부의 `content_status` 만 보면 둘을 구분할 수 없다.** "휴지통" 판정은
  **컨테이너의 상태**로 해야 한다.
- 개별 삭제된 첨부는 Confluence UI 어디에도 안 보이는데 **디스크 파일은 그대로 남아
  있다**(실측: 삭제 후에도 `ver003/.../3670106` 파일 존재). 관리자가 "지웠는데 용량이
  안 준다"고 느끼는 실제 원인 중 하나다.
- 기획서 3.1 의 라벨 5개에 **"삭제됨"이 빠져 있다.** 라벨을 늘리는 것은 기획서
  "라벨 5개를 늘리거나 줄이지 않는다"에 걸리지만, 이건 라벨 축(참조 여부)이 아니라
  **행의 생존 여부**다. 판단: 삭제된 첨부는 목록의 기본 필터에서 빼고, 랭킹 화면에는
  "삭제 대기 n건 · x MB" 를 별도 수치로 보여준다. 라벨은 5개로 유지한다.

## 기획서와 달라진 결정 요약

1. 버전 체인은 `PREVVER → head` 다. 최신 판정은 `PREVVER IS NULL`. (V1)
2. 파일시스템을 읽지 않는다. DB 메타만으로 충분하다. (V2)
3. 직접 SQL 을 v1 에 넣지 않는다. `AttachmentDao#findLatestVersionsIterator()` 를 쓴다. (V3·V4)
4. 참조 스캐너는 매크로를 열거하지 않고 `ri:attachment` 엘리먼트를 전부 걷는다. 예외는
   `gallery` 의 평문 파라미터 하나뿐이다. (V5)
5. "(스페이스 없음)" 버킷이 필요하다. 스페이스 합계 ≠ 인스턴스 총계. (V6)
6. 휴지통 판정은 컨테이너 상태로 한다. 개별 삭제된 첨부는 별도 수치로 뺀다. (V7)
   → 구현 2번에서 뒤집혔다. 그 수치를 만들 방법이 v1 에 없어 화면에서 아예 뺐다.

# 구현하면서 실측한 것

여기부터는 골격(기획서 11장 2~4단계)을 실제로 붙여 보고 알게 된 것이다. 위의 V1~V7 은
착수 전 조사이고, 아래는 코드가 돌아간 뒤의 결과다. 코드 주석이 이 번호를 가리킨다.

## 1. 백그라운드 스레드의 AO 쓰기도 트랜잭션이 필요하다

첫 스캔은 **읽기를 다 끝내고 저장에서** 죽었다.

```
IllegalStateException: No Hibernate Session bound to thread,
    and configuration does not allow creation of non-transactional one here
    at com.atlassian.hibernate.SpringPluginHibernateSessionFactory.getSession
    at ...ScanStore.saveRun(ScanStore.java:81)
```

- 읽기(`findLatestVersionsIterator()` 순회)는 SAL `TransactionTemplate.execute()` 안에서
  **정상 동작했다.** 즉 Confluence 의 SAL 트랜잭션은 백그라운드 스레드에도 호스트
  Hibernate 세션을 붙여 준다.
- **Confluence 의 Active Objects 는 호스트 Hibernate 세션 위에서 돈다.** 그래서 AO 쓰기도
  똑같이 감싸야 한다. `ao.create(...)` 를 트랜잭션 밖에서 부르면 같은 예외가 난다.
- 읽기와 쓰기를 **별도 트랜잭션 두 개**로 나눴다. 하나로 묶으면 대형 인스턴스에서 스캔이
  끝날 때까지 트랜잭션이 열려 있게 되는데 얻는 것이 없다.
- 부수 확인: 예외를 `Throwable` 로 잡아 둔 덕에 실패가 화면에 문구로 나왔다. 잡지 않았다면
  진행률이 RUNNING 에 박혀 화면이 영구 폴링했을 것이다(기획서에 없던, 형제 앱의 교훈).

## 2. `findLatestVersionsIterator()` 는 삭제된 첨부를 돌려주지 않는다

DB 에는 `content_status='deleted'` 인 첨부가 3행 있는데 스캔 결과의 삭제 집계는 0 이었다.
이터레이터가 현재 상태만 준다.

- V7 에서 "삭제 대기 n건 · x MB 를 따로 보여준다"고 판단했는데 **그 수치를 정직하게 만들
  방법이 v1 에 없다.** 남은 경로는 컨테이너를 하나씩 돌며
  `getLatestVersionsOfAttachmentsWithAnyStatus(CEO)` 를 부르는 것뿐이고, 그건 이 앱이
  피하려고 만든 O(페이지 수) 순회다.
- **구조적으로 항상 0 인 칸을 화면에 두지 않는다.** 0 은 "없다"로 읽힌다. 그래서 v1 에서는
  칸과 AO 컬럼과 REST 필드를 전부 뺐고, 대신 화면 하단 한계 문구에 "삭제 표시된 첨부는 이
  합계에 없다"를 적었다. 제대로 세는 것은 v2 다.

## 3. SAL `@WebSudoRequired` 는 Confluence 플러그인 서블릿에 아무 효과가 없다

로그인만 한 세션으로 실측:

| 대상 | 애노테이션만 있을 때 |
|---|---|
| `/admin/console.action` | 302 → `/authenticate.action?destination=...` |
| `/plugins/servlet/attachment-janitor` | **200 (그대로 열렸다)** |

- 형제 앱이 Jira 에서 겪은 것("경로만으로는 웹수도가 안 걸린다")과 같은 함정인데,
  Confluence 에서는 **애노테이션조차 걸리지 않는다.**
- `com.atlassian.confluence.security.websudo.WebSudoManager` 를 서블릿에서 직접 부른다.
  `isEnabled()` 이고 `hasValidSession(request.getSession(false))` 가 거짓이면
  `/authenticate.action?destination=...` 으로 보내고, 통과하면 `markWebSudoRequest(request)`
  로 보안 세션 시간을 연장한다(Confluence 자기 관리 화면과 같은 동작).
- 고친 뒤 실측: 일반 세션 302 → 인증 후 200. **basic 인증 REST 는 그대로 200** — 스크립트와
  폴링이 웹수도에 걸리지 않는다(기획서/형제 앱의 결정 그대로).
- `WebSudoManager` 는 `@ComponentImport` 로 주입된다. OSGi 해석 문제 없었다.

## 4. 성능 — 병목은 첨부 수가 아니라 "버전이 있는 첨부 수"다

`tools/make-testdata.py --bulk N` 으로 첨부를 늘려 두 번 측정했다. **첨부 수는 같고
구버전 수만 다르다.**

| 첨부(최신) | 구버전 행 | 스캔 소요(POST → DONE, AO 저장 포함) |
|---|---|---|
| 2,044 | 17 | **1.19 초** |
| 2,044 | 1,048 | **15.7 / 16.1 / 19.9 초** (3회) |

- 첨부 수가 그대로인데 **13~16배 느려졌다.** 늘어난 것은 `getPreviousVersions()` 호출
  1,031회뿐이다 → **호출 1회당 약 14ms.**
- 분해하면 이렇다.
  - 기본 순회: 첨부 1개당 약 0.5ms (2,000/초)
  - 구버전 조회: **버전이 2 이상인 첨부 1개당 약 14ms (70/초)**
- 즉 `getVersion() > 1` 로 호출을 거른 최적화는 유효하지만, **이 앱이 존재하는 이유인
  "구버전이 쌓인 인스턴스"에서는 그 필터가 걸러 주지 않는다.** 전 첨부에 버전이 있는
  10만 개 인스턴스는 산술적으로 약 24분이다.
- **그러므로 "스캔은 빠르다"고 적으면 안 된다.** 앞선 초안이 2,044/17 한 점만 보고
  "10만 개도 1분 안쪽"이라고 적었는데, 두 번째 점이 그 문장을 뒤집었다.
  화면 문구는 "규모가 큰 인스턴스에서는 업무 시간을 피하라"로 두고, 진행률·취소를
  장식이 아니라 필수 기능으로 취급한다.
- 개선 후보(측정 후에 고른다): 구버전을 첨부마다 묻지 않고 한 번에 가져오는 경로가
  API 인터페이스에는 없다. `AttachmentDao#findAll()` 은 전 버전을 `List` 로 주므로
  쿼리는 1회지만 메모리를 감당해야 한다. 8번의 구현 사실과 함께 판단할 것.

## 8. `findLatestVersionsIterator()` 는 스트리밍이 아니라 `Query.iterate()` 다

바이트코드로 확인했다(`VersionedHibernateObjectDao#findLatestVersionsIterator(String...)`):

```
HibernateTemplate.iterate(String, Object[])   ← Hibernate 의 Query.iterate()
```

- `iterate()` 는 **ID 목록만 한 번에 가져오고, 엔티티는 `next()` 때마다 하나씩** 읽는다.
  즉 우리 스캔은 첨부 1개당 쿼리 1개(= 1 + N)를 쓴다. 4번의 "0.5ms/첨부"가 그 값이다.
- **읽은 엔티티는 트랜잭션이 끝날 때까지 Hibernate 1차 캐시에 남는다.** 우리는 스캔
  전체를 트랜잭션 하나로 감싸므로 **영속성 컨텍스트가 첨부 수에 비례해 커진다.**
  2,044개에서는 문제가 없었지만 **대형 인스턴스의 메모리 거동은 측정하지 못했다.**
  측정하지 않은 것을 "괜찮다"고 적지 않는다.
- 바운드가 필요해지면 트랜잭션을 쪼개야 하는데, 같은 클래스 계열에
  **`findLatestVersionIdsIterator(List<Space>)`** 가 있다 —
  `AbstractHibernateAttachmentDao` 에 있고 **`AttachmentDao` 인터페이스에는 없다.**
  V3 의 "스페이스 단위 조회가 없다"는 *인터페이스에 한해서* 맞는 말이었다.
  구현체에 캐스팅하는 것은 7.12.3 에서 깨질 수 있으므로 v1 에서는 쓰지 않지만,
  스페이스 단위로 트랜잭션을 쪼개는 개선의 출발점은 여기다.
- 참고로 `AttachmentManager` 는 캐싱 델리게이트 여러 겹(`ReadThroughCachingAttachmentDao`
  등)을 거쳐 이 구현에 닿는다. 우리가 보는 것은 그 델리게이트의 동작이다.

## 9. 실패·취소도 행으로 남긴다 (리뷰 반영)

초안은 실패한 실행 아래에 표를 비워 두었는데, 그러면 배너는 "스캔이 실패했다"라고 하고
표는 "아직 스캔한 적이 없습니다"라고 하는 모순된 화면이 나왔다. 고친 규칙:

- **배너는 `latestRun()`**(상태 불문), **표는 `latestCompleteRun()`** 이다.
- 둘이 다르면 `aj.state.stale` 로 "아래 표는 마지막으로 완료된 스캔의 것"이라고 적는다.
- 완료된 실행이 하나도 없으면 "아직 완료된 스캔이 없다"(`aj.state.noresults`)로,
  실행 자체가 없으면 "아직 스캔한 적이 없다"(`aj.state.never`)로 나눈다.
- **취소된 실행도 저장한다.** 저장하지 않으면 화면을 다시 그리는 순간 취소가 없었던
  일이 되고, 이전 스캔의 표만 남는다.

  본다. 거칠지만 스페이스 설명은 짧고 드물다. 한계로 적어 둔다.

## 11. 본문에 HTML 엔티티가 그대로 들어 있다 — 파서가 그냥 죽는다

이 인스턴스 본문 144개 중 **18개에 `&nbsp;`** 가 있었고 `&mdash;` 도 나왔다. 저장 형식은
DTD 가 없는 XML 이라 엔티티 선언이 어디에도 없다. 손대지 않으면 "분석 실패"가 소수가
아니라 사실상 전부가 된다.

- DOCTYPE 내부 서브셋에 HTML4 엔티티를 선언해 넣는 방법도 있지만, **표에 없는 엔티티**
  (다른 앱이 넣은 것)에서 여전히 죽는다. 그래서 선언이 아니라 **치환**을 한다 —
  아는 것은 숫자 참조로 바꾸고 모르는 것은 버린다(`HtmlEntities`).
  본문 글자 한 자가 사라져도 우리가 보는 것은 엘리먼트 구조와 파일명뿐이라 판정이
  달라지지 않는다. 표는 `tools/make-html-entities.py` 가 만든다(248개).
- **파서는 네임스페이스 비인식으로 돌린다.** 저장 형식 조각에는 `ac:` / `ri:` 프리픽스가
  선언 없이 들어 있어서 네임스페이스 인식 파서는 첫 엘리먼트에서 죽는다. 비인식 모드에서는
  프리픽스가 이름의 일부일 뿐이라 아무 선언 없이 읽힌다 — 감싸는 루트 엘리먼트만 있으면 된다.
- DTD 로드와 외부 엔티티는 전부 막는다(XXE). 남이 쓴 문서를 파싱하는 코드다.
- 실측 결과 2,046개 첨부 · 본문 51건에서 **분석 실패 0건**이었다.

## 12. `PageManager` 가 `ContentEntityManager` 를 상속한다 — 둘 다 주입하면 앱이 안 뜬다

```
NoUniqueBeanDefinitionException: No qualifying bean of type
'com.atlassian.confluence.core.ContentEntityManager' available:
expected single matching bean but found 2: contentEntityManager, pageManager
```

과거 버전 조회(`getPreviousVersion`)를 하려고 `ContentEntityManager` 를 따로 주입했더니
플러그인이 기동하지 않았다. `PageManager` 하나만 주입하고 거기서 상속받은 메서드를 쓴다.

## 13. AO 엔티티를 `atlassian-plugin.xml` 의 `<ao>` 에 등록하지 않으면 테이블이 없다

새 엔티티 인터페이스를 만들고 등록을 빠뜨렸더니 스캔이 마지막 단계에서 죽었다.

```
PSQLException: ERROR: relation "AO_13C16C_ATT_ROW_ID_seq" does not exist
```

컴파일도 되고 기동도 되므로 **런타임에만 드러난다.** 엔티티를 추가할 때는 반드시
`<ao>` 목록도 같이 고친다.

## 14. 같은 스페이스에 같은 제목의 블로그를 만들 수 없다

날짜가 다르면 가능할 것으로 보고 픽스처를 만들려 했는데 REST 가 400 을 돌려줬다.
→ **(스페이스, 제목) 은 페이지뿐 아니라 블로그에도 유일하다.** 참조 대상을 제목으로
푸는 인덱스가 모호해질 걱정을 하지 않아도 된다.

## 15. `I18NBeanFactory` 는 플러그인 번들을 본다 — 한영 토글이 성립한다

`I18NBeanFactory#getI18NBean(Locale)` 이 우리 `.properties` 를 읽는지가 언어 토글의
전제였다. 실측: `?lang=ko` / `?lang=en` 으로 설명서와 모든 화면이 각각 한국어·영어로
나왔다. `I18NBean#getTranslationsForPrefix("aj.")` 도 동작해서, **화면에 넘길 문구 키를
손으로 나열하지 않는다** — 나열은 문구를 추가할 때 한쪽을 빼먹어 화면에 키가 그대로
나오는 사고를 만든다.

주의: `{0}` 이 있는 문구는 `MessageFormat` 이 숫자에 자릿수 구분을 넣는다
(1095 → `1,095`). 버그가 아니라 정상이다.

## 17. 성능 — 본문 읽기가 붙어도 감당 가능하다

첨부 2,046개 · 본문 51건(이력 켜면 108건) 기준:

| 설정 | 소요 |
|---|---|
| 기본(이력 끔, 약식 해시) | **20.5 ~ 25 초** (재측정 2026-09-14: 23 · 25초) |
| 이력 검사 + 전체 해시 | **26.8 초** |

- 4번에서 본 대로 지배적인 비용은 여전히 구버전 조회다(이 인스턴스는 구버전 1,048개).
- **측정 편차가 있다.** 같은 조건에서 23 · 25 · 31초가 나왔다. 31초는 atlas-run 을
  내린 직후 첫 실행이었다(호스트 메모리 회수 중). 초 단위로 비교하지 말 것.
- 본문 51건 읽기와 해시 1MB 는 눈에 띄지 않았다. 다만 이 인스턴스는 페이지가 39개뿐이라
  **본문 단계의 확장성은 측정하지 못했다.** `pageManager.getPages(space, true)` 가
  스페이스의 페이지 객체를 전부 메모리에 올리므로 대형 스페이스에서는 여기가 문제가 될
  수 있다. 측정하지 않은 것을 괜찮다고 적지 않는다.
- 저장 행 수: 첨부 2,046 · 근거 53 · 중복 그룹 2. 상세는 최신 완료 실행 하나만 남는 것을
  DB 에서 확인했다(실행 5개 중 `HAS_DETAIL=t` 는 하나).

## 18. 권한 — 새 화면·엔드포인트도 전부 막힌다

비관리자 계정으로 `/space`, `/duplicates`, `/settings`, `PUT /settings`,
`space.csv`, `duplicates.csv` 전부 403. 설정 저장은 상·하한이 걸린다
(keepRuns 9999 → 50, oldVersionCount 0 → 2, staleDays -5 → 1).

## 19. 배포 목표(7.12.3) 컴파일 — 통과

개발은 7.8.1 로 하지만 배포 목표는 7.12.3 이다. 이번에 쓴 API 중 그 사이에 사라진 것이
있으면 기동 후 `NoSuchMethodError` 로 터진다 — 컴파일러가 정적으로 잡을 수 있는 일을
사용자 인스턴스에서 발견하게 두지 않는다.

```
atlas-mvn -o compile -Dconfluence.version=7.12.3 -Dconfluence.data.version=7.12.3
```

오류 0. `AttachmentDao#findLatestVersionsIterator`, `I18NBean#getTranslationsForPrefix`,
`WebSudoManager`, `PageManager#getPreviousVersion`, `BandanaManager`, `Space#getDescription`
모두 7.12.3 에도 그대로 있다. **`pom.xml` 의 기본값은 바꾸지 않는다** — 기본을 7.12.3 으로
올리면 7.8.1 에 없는 API 를 실수로 쓸 수 있다. 이 명령은 릴리스 전 검사로만 쓴다.

## 20. 조회 N+1 과 대량 삭제 — 한 문장으로 묶었다

- **근거 조회.** 스페이스 상세 화면이 첨부마다 근거를 따로 물으면 첨부 2,000개짜리
  스페이스에서 화면 한 번에 조회가 2,000번 나갔다. `ROW_ID IN (...)` 로 900개씩 끊어
  한 번에 읽는다(`ScanStore.refsOf`). 근거가 0건인 첨부는 애초에 목록에 넣지 않는다.
- **상세 삭제.** `ao.delete` 를 행마다 부르면 첨부 10만 건에 삭제문이 20만 개 나간다.
  AO 3.2.4 에 `deleteWithSQL(Class, String, Object...)` 가 있어(`javap` 로 확인) 실행
  단위 삭제는 한 문장이다. 근거 행에는 실행 번호 열이 없으므로 첨부 행 ID 를 `IN` 으로
  끊어 넘긴다.
- 바꾼 뒤 DB 확인: 실행 5개 중 `HAS_DETAIL=t` 하나, 첨부 2,046 · 근거 53 · 중복 그룹 2,
  **끊어진 근거 행 0** (`REF_HIT` 를 `ATT_ROW` 에 left join 했을 때 짝 없는 행 없음).

## 21. 관리 화면 제목은 sitemesh 가 이미 그린다

`atl.admin` 장식은 응답의 `<title>` 을 관리 화면 제목으로 그대로 그린다. 그래서 본문에
`<h1>` 로 같은 문구를 한 번 더 찍으면 **화면 맨 위에 제목이 두 번** 나온다. `<h1>` 을
없앴다. 화면별 제목 구분(설명서 화면)은 `<title>` 만으로 유지된다:

| 화면 | 장식이 그리는 제목 |
|---|---|
| 목록·중복·설정 (en/ko) | Attachment Janitor / 첨부파일 정리 도우미 |
| 설명서 (en/ko) | Attachment Janitor — Help / 첨부파일 정리 도우미 — 설명서 |

머리줄에 남는 것은 언어 토글뿐이라 오른쪽 정렬로 바꿨다.

## 22. UPM 아이콘은 원본 하나에서 두 크기를 만든다

`images/plugin.png`(512x512 RGBA)가 원본이고 `tools/make-icons.py` 가 여기서
`pluginIcon.png`(72) · `pluginLogo.png`(144)를 만든다. 512 를 두 슬롯에 그대로 꽂지
않는 이유는 목록에서 매번 브라우저가 축소하기 때문이다.

빌드 머신에 Pillow 가 있다고 가정하지 않으려고 PNG 를 직접 읽고 쓴다(zlib + 필터 해제
+ 상자 평균). **알파를 곱해 두고 평균한 뒤 되돌린다** — 그냥 평균하면 투명 픽셀의 색이
섞여 테두리에 어두운 띠가 생긴다.

설치 후 UPM 이 실제로 내주는 것을 확인했다:
`/rest/plugins/1.0/<key>/media/plugin-icon` → 200 `image/png` 72x72,
`plugin-logo` → 200 `image/png` 144x144.


## 23. 7.12.3 런타임 대조 — 회귀 없음

`atlas-run -Pconf7123` 으로 7.12.3 을 띄워 7.8.1 과 나란히 쟀다. 결과는 별도 문서:
[01-버전대조-7.8.1-vs-7.12.3.md](01-버전대조-7.8.1-vs-7.12.3.md).

요약: 22항목 중 20 같음, 웹수도 1건은 AMPS 가 인스턴스 전체에서 꺼서 측정 불가,
나머지 1건은 픽스처 이력 차이. **라벨 판정 13/13 일치.** 코드 수정 없음.

19번(컴파일 검사)과 이건 **다른 레버**다. 19번은 "API 가 남아 있나", 이건 "빌드한 jar 이
도나". `pom.xml` 의 `confluence.version`(컴파일)과 `confluence.runtime.version`(실행)이
나뉘어 있는 이유이고, 프로필이 컴파일 축까지 올리면 시험 자체가 무의미해진다.

## 24. 본문 단계의 확장성 — 메모리가 아니라 시간이 문제다

17번에서 "본문 단계의 확장성은 측정하지 못했다"고 적어 둔 것을 실제로 쟀다. AJC 스페이스에
페이지 500개 × 버전 10개를 만들고(`tools/make-testdata.py --bulk-pages 500 --bulk-versions 10`)
축을 나눠 봤다. 힙은 컨테이너 안에서 `jcmd <pid> GC.heap_info`, 스캔 전후로 강제 GC 를 걸어
잰다. **jira 컨테이너는 띄워 둔 채로 쟀다** — 실사용 환경도 같은 서버에 Jira 가 떠 있다.

| 조건 | 첨부 | 본문 | 소요 | 스캔 중 최고 힙 | 풀GC 후 잔존 |
|---|---|---|---|---|---|
| 기준선 | 2,046 | 51 | 31초 | +328 MB | ±0 |
| 페이지 500 추가, 이력 끔 | 2,546 | 553 | 46초 | +356 MB | ±0 |
| 같은 데이터, 이력 끔 (재측정) | 2,546 | 553 | 47초 | +345 MB | +1 MB |
| **이력 켬** | 2,546 | **5,131** | **338~420초** | **+393 MB** | +13 MB |

(Confluence 힙 상한 2GB · G1. 기준선은 스캔 직전 풀GC 후 400~430MB.)

**최고 힙은 2초 간격 샘플링이라 하한이다** — 샘플 사이에 더 올라갔을 수 있다. 정확한
쪽은 잔존값이고, "누수 없음 · 쪼갤 필요 없음"을 받치는 것도 그쪽이다.

이력 켠 스캔은 세 번 재서 **338 · 344 · 420초**가 나왔다. 같은 데이터·같은 설정이다.
초 단위로 비교하지 말 것.

### 결론 1 — 메모리는 안 터진다. 트랜잭션을 쪼개지 않는다

본문이 51 → 5,131 로 **100배**가 되는 동안 최고 힙은 +328MB → +393MB 로 **65MB** 늘었다.
본문 하나당 약 13KB 의 일시적 비용이고, 풀GC 후 잔존은 사실상 0 이다(누수 없음).

그래서 8번에서 우려한 "스캔 전체가 트랜잭션 하나라 1차 캐시가 첨부 수에 비례해 커진다"는
**본문 축에서는 문제가 아니다.** 스페이스 단위로 트랜잭션을 쪼개는 개조는 하지 않는다 —
쪼개면 `findLatestVersionsIterator` 가 준 엔티티가 detach 되고 `getPreviousVersions()` 가
닫힌 세션에서 지연 로딩을 시도하게 된다. 없는 문제를 풀려고 그 위험을 지지 않는다.

**첨부 축은 여전히 미측정이다.** 2,546개까지만 봤다. 이 표는 본문 축에 대한 답이지
"10만 개 인스턴스에서 괜찮다"는 답이 아니다.

### 결론 2 — 비용은 본문 개수에 정비례한다. 이력 검사가 그걸 10배로 만든다

단계별로 쪼개 보면 어디가 비싼지 분명하다(이력 켬, 본문 5,131):

| 단계 | 소요 | 비중 |
|---|---|---|
| ATTACHMENTS | 18.4초 | 5% |
| **BODIES** | **316.0초** | **93%** |
| MATCH · DUPLICATES | 0.5초 미만 (샘플링에 안 잡힘) | — |
| SAVE | 3.7초 | 1% |

본문 하나당 45~62ms 다. **현재 페이지든 과거 버전이든 값이 비슷하다** — 즉 이력 검사가
느린 이유는 이력이 특별히 비싸서가 아니라 **읽을 본문을 10배로 만들기 때문**이다.

그래서 이력 검사는 기본값 꺼짐이 맞고, 화면이 [고아] 를 "고아(이력 미검사)" 로 표기하는
설계도 맞다. 켤 때 몇 분이 걸린다는 것을 설명서와 README 가 말해야 한다.

## 25. 진행률과 취소가 본문 단계에서 무의미했다 (수정)

24번을 재다가 발견했다. 이력을 켠 스캔에서 화면이 **"ATTACHMENTS 2400/2546 · 94%" 에서
80초 넘게 멈춰** 있었고, 취소를 눌러도 **5분 13초** 뒤에야 먹었다.

원인 셋:

1. 첨부 단계 진행률이 200건마다만 갱신되어 마지막 자투리(146건)를 안 찍었다. 그래서
   다음 단계가 길면 "2400/2546" 에 멈춰 보인다.
2. 본문 단계 진행률과 취소 확인이 **스페이스 사이에서만** 일어났다. 페이지 500개짜리
   스페이스 하나를 도는 5분 동안 화면은 이전 단계를 그대로 보여주고 취소도 안 먹는다.
3. 중복 단계도 같았다(진행 콜백 없음, 취소 확인 없음).

고친 것:

- `BodyWalker.Watcher` — 페이지마다 취소를 확인하고 20건마다 진행을 알린다. 이력 순회
  안에서도 확인한다(한 페이지에 200버전이면 거기도 길다).
- `DuplicateFinder.Watcher` — 같은 모양. 취소되면 **그룹을 만들지 않고 돌아간다**.
  반쯤 해시한 결과를 중복 목록이라고 내놓는 것이 검사하지 않은 것보다 나쁘다.
- 각 단계 진입 시점에 단계를 먼저 세운다. 첨부 단계 마지막 자투리도 찍는다.
- **본문 단계는 비율을 지어내지 않는다.** 분모가 스페이스 수라 실제 진척과 안 맞는다
  (큰 스페이스 하나에서 0% 로 앉아 있게 된다). `percent()` 가 -1(모름)을 내고 화면은
  흐르는 줄무늬 막대를 그린다. 대신 **읽은 본문 수**를 문구로 계속 올린다.
- **취소·실패에 100% 를 찍지 않는다.** 끝난 것과 완주한 것은 다르다. 진행 막대가
  "다 됐다"고 말하면 바로 위의 실패 배너와 정면으로 어긋난다.

측정(수정 후 빌드에서 다시 확인): 취소 반영 **5분 13초 → 1초**. 본문 단계에서
`percent` 가 -1 로 나오고 `bodies` 가 0 → 900 으로 계속 올라간다. 취소된 실행은
`percent=-1 · bodies=904` 로 어디까지 읽었는지 남는다.

**흐르는 막대 자체는 브라우저에서 눈으로 확인하지 않았다** — CSS 애니메이션이라
curl 로는 안 보인다. 서버가 -1 을 내는 것과 JS 가 그때 `aj-progress-unknown` 을 붙이도록
쓰여 있는 것까지가 확인된 범위다.

## 26. 남은 N+1 을 묶었다

중복 화면이 그룹마다 구성원을 따로 조회했다(`attachmentsWithHash`). 근거 조회(20번)와
같은 방식으로 `CONTENT_HASH IN (...)` 900개씩 끊어 한 번에 읽는다(`attachmentsByHash`).
CSV 경로도 같은 것을 쓰고 있었으므로 함께 고쳤다.

첨부 2,546 · 근거 5,080 상태의 화면 응답: 스페이스 목록 31ms, **AJC 상세(첨부 500 ·
근거 500) 380ms**, 중복 26ms, 중복 CSV 25ms.

## 27. 스페이스 로고는 첨부다 — 그리고 앱이 그걸 [고아] 라고 불렀다

V6 에서 "스페이스 로고는 SPACEDESCRIPTION 컨테이너의 첨부일 것"이라고 적고 로고를 설정한
스페이스가 없어 미실측으로 뒀다. 이번에 AJA 에 로고를 올려 확인했다.

- `AbstractLogoAction` 이 `AttachmentManager` 와 `getContentToAttachLogoTo()` 를 쓴다 —
  로고는 **정말로 첨부**다.
- 올린 뒤의 행: 컨테이너 타입 `SPACEDESCRIPTION`, **첨부 파일명이 스페이스 키(`AJA`)** 다.
  Confluence 자신도 `/rest/api/space/AJA?expand=icon` 에서
  `/download/attachments/3670080/AJA?version=1&...` 로 답한다.
- 업로드 경로는 `POST /spaces/uploadspacelogo.action` (`atl_token` 필요, `newLogo` 필드).
  `/rest/api/content/<스페이스설명 id>/child/attachment` 로 직접 붙이는 것은 500 이다.

**그리고 앱이 이 로고를 [고아] 로 찍었다.** 당연하다 — 어느 본문도 로고를 가리키지 않는다.
로고는 스페이스 설정이지 본문 참조가 아니다. 하지만 그 결과 앱은 관리자에게 "이 파일은
아무도 안 쓴다"고 말하게 되고, **지우면 스페이스 머리글이 눈에 띄게 깨진다.** [고아] 가
과다 집계 쪽으로 기우는 실제 사례이고, 고아 삭제를 미뤄 둔 이유이기도 하다.

### 고친 방식 — 참조를 하나 만들어 붙인다

`RefKind.SPACE_LOGO` 를 더하고, 스캔이 스페이스를 돌 때 근거를 하나 합성한다.

- **파일명을 추측하지 않는다.** `SpaceManager.getLogoForSpace(key)` 가
  `isCustomLogo()` 이면 `getDownloadPath()` 에서 이름을 뗀다 — Confluence 자신의 답이다.
  컨텍스트 경로 · 질의 문자열 · 퍼센트 인코딩을 다루는 것을 `BodyWalkerTest` 가 잡는다.
- 같은 컨테이너에 붙었지만 로고가 **아닌** 파일은 그대로 [고아] 다. 그건 정말로 안 쓰인다.
  (그런 파일을 만들 방법을 찾지 못해 **이 경우는 실측하지 못했다** — 코드가 로고 파일명
  하나에만 근거를 붙인다는 것까지가 확인된 범위다.)

확인: `AJA | container=spacedesc | label=active | refs=[(spacelogo, Attachment Janitor Fixture A)]`.
docs/01 의 라벨 13건은 전부 그대로다(회귀 없음).

## 28. 페이지 템플릿은 `ri:attachment` 를 가질 수 없다 — 스캔하지 않는다

V6 에서 "템플릿 본문은 `pagetemplates.content` 에 따로 있으니 스캔하려면 별도 경로가
필요하다"고 적었다. API 는 있다 — `PageTemplateManager.getGlobalPageTemplates()` 와
`getPageTemplates(Space)` 는 페이지 순회 없이 바로 목록을 준다. 그런데 **스캔할 것이 없다.**

템플릿 세 개를 만들어 확인했다(`POST /pages/templates2/docreatepagetemplate.action`,
`title` · `titleWritten` · `wysiwygContent` 필드, 본문은 **에디터 형식**이어야 한다):

| 넣은 것 | 저장된 것 |
|---|---|
| `data-linked-resource-default-alias="tmpl-global.png"` (해석 불가) | `<ri:url ri:value="/download/attachments/1/tmpl-global.png?api=v2" />` |
| 같은 것, 스페이스 지정 | 같음 |
| **실재하는 페이지·첨부 id 로 완전히 해석 가능한 참조** | `<ri:url ri:value="/download/attachments/3670084/orphan.png?api=v2" />` |

세 번째가 결정적이다. 해석에 필요한 것이 다 있어도 Confluence 는 `ri:attachment` 를 쓰지
않는다. 당연하다 — `ri:attachment` 는 "이 컨텐츠에 붙은 첨부"라는 뜻인데 **템플릿에는
컨테이너가 없다.** 그래서 템플릿 본문을 `ri:attachment` 로 훑으면 구조적으로 0 건이다.

→ **템플릿 스캔을 넣지 않는다.** 넣어도 아무것도 못 찾는다.

### `ri:url` 을 따라가지 않는 이유

`/download/attachments/<id>/<name>` 은 결정적이라 파싱이 쉬워 보인다. 하지만 그건 **다른
종류의 증거**다 — 구조적 참조가 아니라 문자열이다. 한 번 따라가기 시작하면 본문의
`<a href="/download/attachments/…">`, 붙여넣은 내려받기 링크, `?version=N` 고정,
`/download/thumbnails/`, 컨텍스트 경로까지 전부 다뤄야 한다. V5 에서 `ri:attachment` 를
훑기로 한 근거는 "Confluence 가 그 뜻을 보장한다"였고, URL 에는 그 보장이 없다.

넣는다면 별도 기능으로 한계와 함께 논의할 일이지 여기서 끼워 넣을 것이 아니다.
(증거 표본으로 `AJ Qualified Template` 하나를 인스턴스에 남겨 뒀다.)

## 29. 삭제됐지만 디스크에 남은 첨부 — 여전히 셀 수 없다. 이번엔 숫자로 안다

2번에서 "정직하게 셀 방법이 없다"고 적었다. 이번에 그 말에 숫자를 붙였다.

| | 행 | 바이트 |
|---|---|---|
| `content_status = 'current'` (앱이 세는 것) | 2,546 | 5,643,290 |
| `content_status = 'deleted'` | **8** | **3,892** |

그 8건이 어디 있는지가 핵심이다:

| 첨부 상태 | 컨테이너 상태 | 수 |
|---|---|---|
| deleted | 페이지가 **휴지통**(deleted) | **7** |
| deleted | 페이지는 살아 있음(current) | 1 |

- 1건은 `getLatestVersionsOfAttachmentsWithAnyStatus(page)` 로 잡을 수 있다. 본문 단계가
  이미 모든 현재 페이지를 도니 거기에 끼울 수 있지만, **페이지마다 쿼리 한 번**이 늘고
  실측 24번대로 본문 단계는 이미 전체의 93% 다.
- **7건은 그 방법으로도 못 잡는다.** 컨테이너가 휴지통에 있어 `getPages(space, true)` 가
  주지 않고, `PageManager.getPageInTrash(String, String)` 은 제목을 알아야 한다.
  휴지통 전체를 주는 API 가 인터페이스에 없다. `HibernateAttachmentDao` 에도 없다.

→ **v1 의 한계로 그대로 둔다.** 87%(8건 중 7건)를 못 세는 방법을 O(페이지 수) 비용으로
넣는 것은 정직하지도 싸지도 않다. 화면 하단 한계 문구를 그대로 유지한다.

### 보정 (실측 32번을 재다가 알게 된 것)

위 표는 **머리 행만** 센 것이라 실제 잔여를 과소평가한다. 첨부 전체 삭제
(`removeattachment`)는 **머리만 `deleted` 로 바꾸고 구버전 행과 파일은 전부 그대로 둔다.**

```
버전 1..7 짜리 첨부를 통째로 삭제한 뒤
  DB : 1..6 은 content_status='current' 그대로, 7(머리)만 'deleted'
  디스크: 1 2 3 4 6 7  — 하나도 안 지워짐
```

그래서 실제 잔여는 "머리 + 그 머리를 가리키는 모든 구버전"이다. 이 인스턴스 기준:

| | 행 | 바이트 |
|---|---|---|
| 삭제 표시된 머리 | 9 | 4,601 |
| 그 머리들에 딸린 구버전 | **5** | **1,645** |
| 합계 | 14 | **6,246** |

머리만 세면 4,601 바이트지만 실제로 디스크에 남은 것은 **6,246 바이트**, 36% 더 많다.
한계 문구는 "삭제 표시된 첨부는 이 합계에 없다"로 충분하지만, **나중에 이걸 세게 되면
머리만 세면 안 된다**는 것을 여기 적어 둔다.

## 30. 정정 — Confluence 에 첨부 구버전 삭제 UI 가 <b>있다</b>

계획서 9장이 "첨부 구버전 삭제는 Confluence 의 UI 가 없다"고 적었고 로드맵도 그 말을
근거로 삼았는데, 확인해 보니 틀렸다.

- `xwork.xml` 에 `confirmattachmentversionremoval` · `removeattachmentversion` 이 있다
  (`RemoveAttachedFileVersionAction`).
- `/pages/confirmattachmentversionremoval.action?pageId=<id>&fileName=<name>&version=<n>` 이
  HTTP 200 으로 열리고 확인 폼이 나온다.

**한 번에 한 버전이다.** 그래서 이 앱의 가치는 "Confluence 가 못 하는 일"이 아니라
**"어디에 얼마나 쌓였는지 보여주는 것"과 "한 번에 처리하는 것"** 두 가지다.
`spec.xlsx` 구버전 15개면 확인 화면 15장, 이 인스턴스의 구버전 1,048개면 1,048장이다.

버전 단위 <b>휴지통은 없다</b>. `trash(Attachment)` 는 첨부 전체용이고 버전을 지우면
`removeAttachmentVersionFromServer` 로 영구 삭제다 — 되돌릴 수 없다.

## 31. 구버전 삭제가 현재 본문을 깨뜨릴 수 있는가 — 구조적으로 없다

구버전 정리의 안전 기준을 정하려고 "현재 페이지 본문이 특정 버전을 가리킬 수 있는가"를
확인했다. 답은 **없다**, 그리고 그건 표본이 아니라 데이터 모델이 보장한다.

- `AttachmentResourceIdentifier` 의 필드는 **파일명과 컨테이너뿐이다.** 버전 필드가 없다.
  즉 `<ri:attachment>` 로는 버전을 고정할 수 없다.
- 이 인스턴스 본문 5,184건에서 실제 `<ri:attachment ...>` 속성을 세면 `ri:filename=` **하나**뿐
  (83건). `version-at-save` 0건.

→ **구버전을 지워도 `ri:attachment` 참조는 절대 안 깨진다.** 최신 버전이 남고 참조는
파일명으로 풀리기 때문이다. 라벨([활성]/[위험]/[고아])은 구버전 정리의 안전과 **무관하다.**

### 남는 구멍 하나 — 버전 고정 URL

본문이나 외부 시스템이 `/download/attachments/<id>/<name>?version=3` 으로 직접 링크하면
그 링크는 깨진다. 이 인스턴스에는 0건이지만(`ri:url` 에 `version=` 이 든 본문 없음)
**구조적 보장이 아니라 이 인스턴스의 사정일 뿐이다.** 우리는 URL 을 따라가지 않으므로
(실측 28번) 감지할 수 없다 — 한계로 적어야 한다.

### 되돌릴 수 없다

버전 단위 휴지통은 없다(실측 30번). 구버전 삭제는 영구다. 페이지는 안 깨지지만
**이전 버전으로 되돌릴 능력이 사라진다.** 안전장치는 "무엇을 지울 수 있나"가 아니라
"몇 개를 남길 것인가"여야 하는 이유다.

## 32. 구버전 삭제의 실제 동작 — 그리고 Confluence 는 최신 버전을 지키지 않는다

구버전 정리를 설계하기 전에 `removeAttachmentVersionFromServer` 가 실제로 무엇을 하는지
쟀다. `probe.bin` 을 AJA/spec 에 8번 올려 버전 8개를 만들고 하나씩 지워 봤다.

### 버전 행의 모양 (V1 재확인)

```
contentid | version | prevver
  3678777 |       1 | 3678776   <- 구버전은 전부 머리를 가리킨다
  ...     |     ... | 3678776
  3678776 |       8 |           <- 머리만 prevver 가 비어 있다
```

구버전 행도 **자기 버전 번호를 갖는다.** 그래서 정렬 기준이 있다.

### 중간 버전(5)을 지웠을 때

| | 결과 |
|---|---|
| DB 행 | **사라진다.** 8행 → 7행 (`content_status='deleted'` 로 남지 않는다) |
| 디스크 파일 | **사라진다.** 파일명은 버전 번호다: `1 2 3 4 6 7 8` |
| 번호 재부여 | **없다.** 6·7·8 이 그대로. 5번 자리가 빈다 |
| `prevver` 체인 | 그대로 |

→ 회수 용량은 **즉시 실제로 회수된다**(휴지통 경유가 아니다). 버전 번호는 **안정적인
식별자**라서 미리보기와 실행 로그에 그대로 쓸 수 있다.

### 최신 버전(8)을 지웠을 때 — **막지 않는다**

```
버전 8 삭제 시도 → HTTP 302 (성공)
남은 것: 1 2 3 4 6 7   ·  버전 7 이 머리가 됨(prevver 비었음)
디스크:  1 2 3 4 6 7
```

**Confluence 는 거부하지 않는다.** 첨부가 사라지지는 않지만 사람들이 내려받는 내용이
**조용히 한 버전 뒤로 되돌아간다.** 페이지는 안 깨지고 경고도 없다 — 그래서 더 나쁘다.

이건 설계에 직접 영향을 준다:

- **`CleanupService` 는 머리를 절대 `removeAttachmentVersionFromServer` 에 넘기지 않는다.**
  삭제 대상은 `getPreviousVersions(head)` 가 준 것에서만 고르고, 호출 직전에
  `version < head.getVersion()` 을 한 번 더 확인한다. 두 겹으로 막는다.
- 유지 개수 N 산술의 버그가 곧바로 **살아 있는 파일의 내용 변경**이 된다.
  산술은 Confluence 없이 도는 단위 시험으로 못 박는다.
- 삭제 순서는 **오래된 것부터**. 도중에 죽어도 최근 이력이 남는다.
- `getPreviousVersions()` 의 목록 순서에 기대지 않고 **버전 번호로 직접 정렬**한다.
  순서가 문서화돼 있지 않고, 틀리면 위 사고가 난다.

  실패는 기록에 남지만 **그 전까지 DC 에 배포하면 안 된다.**

## 34. 버그 — 정리한 파일에 체크박스가 남고 단추가 먹통이었다 (사용자 제보)

재현: `spec.xlsx` 를 최근 3개 유지로 정리 → 표에 체크박스가 그대로 남음 → 다시 골라
"지울 것 미리보기" 를 눌러도 **아무 반응이 없음**.

원인이 셋이었고 전부 진짜 결함이다.

1. **표가 거짓말을 한다.** 화면은 저장된 스캔을 그리는데, 방금 우리가 지운 것을 그 스캔은
   모른다. 정리 뒤에도 `oldVersionCount=27` 이라고 말하고 체크박스는 그 값으로 그려졌다.
   (DB 실측: 표 27, 실제 2)
2. **유지 개수를 안 본다.** 체크박스 조건이 `oldVersionCount > 0` 이었다. 구버전 2개짜리
   파일에 "최근 3개 유지"면 지울 것이 **0** 인데도 체크박스와 단추가 살아 있었다.
3. **빈 미리보기의 응답이 화면 밖에 있다.** `fileCount=0` 이면 경고를 냈지만 그 자리가
   **페이지 맨 위 배너**였다. 표를 보고 있으면 안 보인다 — "반응이 없다" 로 느껴진다.

### 고친 것

- 체크박스 조건을 `removableAt(row, keep) = oldVersionCount - (keep - 1) > 0` 으로 바꿨다.
  유지 개수를 바꾸면 표를 다시 그리고, 지울 것이 없어진 행의 선택은 버린다.
- `POST /cleanup` 이 **파일별 내역**(`done: [{attachmentId, versionsRemoved, bytesRemoved}]`)
  을 돌려준다. 화면이 그만큼 표의 수치를 깎아 그린다. 서버가 저장된 스캔을 고쳐 쓰지는
  <b>않는다</b> — 그러면 스캔한 적 없는 상태를 스캔 결과인 것처럼 보여주게 된다.
  새 스캔이 저장되면(`shown.finishedAt` 이 바뀌면) 그 기억을 버린다.
- 빈 미리보기 안내를 **단추 옆에** 낸다(위쪽 배너에도 그대로 낸다).
- 정리 줄이 고른 개수만이 아니라 **지워질 버전 수**를 함께 보인다. 0 이면 단추가 잠긴다.

### 검증 (버전 8개짜리 `bugcheck.bin`)

| 단계 | 결과 |
|---|---|
| keep=3 1차 | 미리보기 5개(`1,2,3,4,5`) → 실행 `done=1 versions=5`, 내역 반환 |
| keep=3 2차 | `fileCount=0` → **단추가 잠겨 눌릴 일이 없다** |
| keep=2 | 지울 1개(`6`) → **체크박스가 다시 나온다** |
| 표 vs 실제 | 스캔 기준 7, 화면은 `done` 으로 2 로 깎아 그림, DB 실제 3버전 |

`RemovableAtTest` 가 화면 식과 `VersionPlan` 의 실제 삭제 개수를 **구버전 0~30 × 유지
1~32 전 조합**에서 대조한다. 둘이 어긋나면 다시 "누를 수 있는데 아무 일도 안 일어나는
단추"가 생기기 때문이다.


## 35. DC 클러스터 잠금 — 노드가 하나여도 고쳐야 했던 것

`AtomicBoolean` 하나로 중복 실행을 막고 있었다. **JVM 하나 안에서만 참이다.** Data Center
는 같은 DB 와 같은 공유 홈을 보는 노드 여러 대라, 그 변수는 노드마다 따로 있다.

### DC 에서 실제로 깨지는 것 셋

| 조합 | 무슨 일이 나나 | 심각도 |
|---|---|---|
| 스캔 × 스캔 | 두 노드가 각각 202 를 받고 전체 순회를 돈다. `ScanRun` 이 두 개 | 낭비 |
| **정리 × 정리** | **유지 개수 아래로 내려갈 수 있다** | 되돌릴 수 없음 |
| 스캔 × 정리 | 스캔이 정리 중간 상태를 저장하는데 그 실행에는 상함 표시가 안 붙는다 | 조용한 거짓말 |

**정리 × 정리가 왜 위험한가.** "실행 시점에 버전 수를 다시 읽어 미리보기와 다르면
멈춘다"(33번)는 검사가 **노드 사이에서는 원자적이지 않다.** A 가 v1~v5 를 하나씩 지우는
도중 B 가 다시 읽으면 B 는 자기가 본 상태 기준으로 맞는 계획을 세우고, 둘의 삭제가
겹쳐 최종적으로 유지 개수보다 적게 남을 수 있다.

**다만 현재 버전은 안 지워진다.** `victim.getVersion() >= head.getVersion()` 거부(32번)가
각 노드 안에서 그대로 걸린다. 이 경합으로 페이지 내용이 조용히 바뀌지는 않는다 — 잃는
것은 되돌릴 여지 쪽이다.

**스캔 × 정리가 왜 안 잡히나.** `markStale()` 은 **완료된** 실행에 표시를 다는데, 동시에
도는 스캔은 아직 완료 전이라 표시할 대상이 없다. 끝나고 나면 방금 것으로 보이는, 실제로는
정리 중간 상태인 표가 남는다.

### 잠금 이름을 하나만 둔 이유

스캔용·정리용으로 나누면 위 표의 셋째 줄(스캔 × 정리)을 따로 막아야 한다. 그런데
**"지금 스캔 중"이라는 사실은 DB 어디에도 없다** — `AjScanRun` 행은 DONE/CANCELLED/FAILED
일 때만 쓰기 때문에, 다른 노드에서 도는 스캔은 조회할 방법이 없다. 이름 하나
(`co.bskim.confluence.attachment-janitor.work`)로 셋을 한꺼번에 배타로 만들면 그 문제가
사라진다. 잠금 이름은 인스턴스 전체에서 유일해야 해서 plugin key 를 앞에 붙였다.

**동작이 하나 바뀌었다**: 전에는 정리만 스캔 중에 409 였는데, 이제 **스캔도 정리 중에
409** 다.

### 함정 — 잡은 스레드가 놓아야 한다

`ClusterLock` 은 `java.util.concurrent.locks.Lock` 을 상속한다. 두 호스트 구현이 모두
소유자를 따지는 잠금이라 **다른 스레드가 `unlock()` 하면 예외이거나 안 풀린다.**
스캔은 HTTP 스레드가 시작하고 몸통은 워커 스레드에 있어서, 요청 스레드에서 잡으면 놓을
곳이 없다. 그래서:

- **워커 스레드가 `tryAcquire()` 한다.** 요청 스레드는 `CountDownLatch` 로 "잡았나"만
  건네받아 202 와 409 를 가른다(한도 30초).
- **잠금을 잡은 뒤에만 진행률을 RUNNING 으로 세운다.** 순서를 뒤집으면 시작하지도 않은
  스캔을 화면이 영원히 폴링한다. 실측으로 확인했다(아래 표 3행).
- `WorkLock.release()` 는 **안 쥔 스레드가 불러도 조용하다.** 그래야 `finally` 에 그냥
  놓을 수 있다. 소유자 판정은 **우리 필드로 한다** — 처음에는 호스트의
  `isHeldByCurrentThread()` 를 썼고 그게 DC 에서 영구 잠금이었다(**36번**).
- `getLockForName()` 은 한 번만 부르고 캐시한다. 비용 때문이고 동일성 때문은 아니다 —
  DC 구현은 부를 때마다 새 객체를 주며 잠금의 실체는 이름(맵 키)이다.
- 잠금 서비스가 던지면 **못 잡은 것으로 친다.** 지우는 작업의 문지기라서 열어 두는 쪽이
  아니라 막는 쪽으로 틀린다.

### 실측 (docker 7.8.1, 단일 노드)

| 시험 | 결과 |
|---|---|
| 동시 스캔 3발 | `202 / 409 / 409`, 본문 `{"error":"busy"}` |
| 스캔 도는 중 정리 | `409 busy` |
| **정리(250파일, 12초) 도는 중 스캔** | `409 busy`, **진행률은 CANCELLED 유지 — RUNNING 으로 안 넘어감** |
| 스캔 DONE 뒤 | 다음 스캔 `202` (잠금 풀림) |
| 스캔 CANCELLED 뒤 | 다음 스캔 `202` (잠금 풀림) |
| 정리 끝난 뒤 | 스캔 `202` (잠금 풀림) |
| 그 정리의 결과 | 250 파일 · 250 버전 · 1,024,000 바이트, 건너뜀 0 · 실패 0 |

`@ComponentImport ClusterLockService` 가 걸린 채 **앱이 활성화됐다** — 번들이
`com.atlassian.beehive` 를 임포트하는데 호스트가 안 내주면 앱이 비활성으로 남는다.
그래서 활성화 자체가 "Server 에서도 이 서비스가 있다"의 증거다. `beehive-api` 는
Confluence 가 `provided` 로 이미 딸려 보내므로(2.0.0, 컴파일 경로에 이미 있었다)
pom 에 더한 것이 없고, Import-Package 도 버전 범위 없이 `com.atlassian.beehive` 하나다.

### 7.12.3 에서도 같은가 (atlas-run, H2)

| 시험 | 7.8.1 (docker/PG) | 7.12.3 (atlas-run/H2) |
|---|---|---|
| 앱 활성화 (beehive 임포트 해소) | 됨 | **됨** |
| 동시 스캔 3발 | 202/409/409 | **202/409/409** |
| 스캔 끝난 뒤 다시 스캔 | 202 | **202** |
| 로그에 `IllegalMonitorStateException` 등 | 없음 | **없음** |

7.12.3 에서 정리 쪽(웹수도가 필요한 경로)은 돌리지 않았다 — AMPS 가 웹수도를 끄기 때문에
(실측 23번) 거기서 재는 것이 7.8.1 보다 덜 정확하다. 잠금 자체는 같은 객체를 쓰므로
방향만 다르고 성질은 같다.

### 검증 못 한 것 — 정직하게

- **노드 두 대의 실제 경합.** 여기에는 클러스터가 없다. `WorkLockTest` 는 노드 대신
  **스레드 두 개**로 본다 — 성질(하나만 들어간다 · 잡은 쪽만 놓는다 · 못 잡으면 안 기다린다)
  은 같지만 **교차 JVM 을 증명하지는 않는다.**

### 부수 관찰 — 큰 배치 하나가 정리 기록을 밀어낸다

`AjActionLog` 는 **파일 단위로 한 행**이다. 이 시험의 250파일 배치가 `ACTION_LOG_PAGE=200`
을 혼자 채워서, `GET /cleanup/log` 가 **그 배치만** 돌려준다 — 이전 배치 넷은 DB 에 그대로
있는데 화면에서 사라졌다. 되돌릴 수 없는 작업의 흔적을 보여주는 곳이라 이건 다시 볼 값어치가
있다(배치 단위 요약 + 펼치기, 또는 배치 기준 페이지네이션). **지금은 고치지 않았다.**
- **잠금을 쥔 채 노드가 죽었을 때의 회수.** Confluence 구현에 달렸고 이 API 에는 임대
  시간이 없다.
- **노드가 다르면 진행률도 취소도 안 된다.** A 가 스캔하는 동안 B 에 붙은 화면은
  아무것도 못 보고, `DELETE /scan` 도 자기 JVM 의 `cancelRequested` 만 세우므로 **B 에서는
  A 의 스캔을 멈출 수 없다.** 둘 다 진행 상태가 메모리에만 있어서다. 고치려면 시작 시점에
  RUNNING 행을 써야 하는데, 그러면 노드가 죽었을 때 영영 안 지워지는 RUNNING 행이 배너에
  남는다 — 규칙 13 이 막는 바로 그 상태다. **안 고치고 한계로 적는다.**
- **스캔 도중 앱을 끄거나 올려 깔았을 때.** 워커는 데몬 스레드이고 UPM 이 번들을 비활성화해도
  스레드를 죽이지는 않는다. 다음 `ScanStore` 접근에서 던져 `catch (Throwable)` → `save(FAILED)`
  → `finally` 의 `release()` 로 풀릴 가능성이 높지만 **관찰하지 않았다.** 살아 있는 노드가
  잠금을 쥔 채 남는 유일한 경로라 DC 로 갈 때 다시 볼 것 — `@PreDestroy` 에서
  `cancelRequested` 를 세우는 것이 깔끔한 대응이다.


## 36. DC 에서만 터지는 결함 — `isHeldByCurrentThread()` 는 Hazelcast 구현에 없다

**단일 노드 시험이 전부 통과한 뒤에, 코드를 읽어서만 찾았다.** 커밋 전 리뷰에서 "구조적으로
잠금을 놓지 못하는 경로가 있나"를 물었고, 답을 코드가 아니라 호스트 구현에서 찾았다.

### 무엇이 틀렸나

처음 `WorkLock.release()` 는 이렇게 생겼다:

```java
if (lock != null && lock.isHeldByCurrentThread()) { lock.unlock(); }
```

`isHeldByCurrentThread()` 는 `com.atlassian.beehive.ClusterLock` 인터페이스에 선언돼 있어
당연히 답할 줄 알았다. **DC 구현은 답하지 않는다.** `confluence-cache-hazelcast-7.8.1.jar` 을
꺼내 `javap` 로 읽으면:

| `HazelcastDualLock` | 구현 |
|---|---|
| `tryLock()` | `IMap.tryLock(key)` |
| `unlock()` | `IMap.unlock(key)` |
| `lock()` | `IMap.lock(key)` — 임대 시간 없음 |
| **`isHeldByCurrentThread()`** | **`throw new UnsupportedOperationException()`** |
| `lockInterruptibly()` · `newCondition()` | 같이 `UnsupportedOperationException` |

그러니 DC 에서는 `release()` 가 예외 → `catch (Throwable)` 이 삼키고 로그만 남김 →
**`unlock()` 에 닿지 않음 → 첫 스캔이 끝난 뒤 잠금이 영영 안 풀림.** 두 번째 스캔부터
전부 409, 정리도 409. 살아 있는 노드가 잡고 있으니 Hazelcast 도 회수하지 않는다.

Server 는 `ReentrantLock` 계열이라 `isHeldByCurrentThread()` 가 잘 답한다. 그래서
docker 7.8.1 · atlas-run 7.12.3 의 여섯 가지 시험(35번)이 **전부 통과하면서 아무것도
증명하지 못했다** — Server 와 DC 는 잠금의 *범위* 만 다른 게 아니라 **API 지원이 다르다.**

### 고친 것

- 소유자를 **우리가 직접 기억한다**(`volatile Thread owner`). `tryAcquire()` 가 성공하면
  적고, `release()` 는 `owner == currentThread()` 일 때만 `unlock()` 한다. 두 구현이 공통으로
  지원하는 것은 `tryLock()`·`unlock()` 둘뿐이고 이제 그 둘만 부른다.
- **같은 스레드의 두 번째 `tryAcquire()` 는 거절한다.** 두 구현이 모두 재진입 잠금이라
  허락하면 보유 횟수가 2 가 되고 `release()` 한 번으로는 안 풀린다. 지금 그런 호출은 없다 —
  생기는 날 조용한 영구 잠금이 되지 않게 미리 막았다.
- 스캔 워커에서 **잡은 순간부터 놓을 때까지를 try 하나**로 묶었다. 잡은 뒤 진행률을 세우는
  사이에 던지면 놓지 못하는 틈이 있었다.
- `WorkLockTest` 는 이제 **가짜 잠금 둘**로 돈다 — `ReentrantLock` 처럼 전부 답하는 것과,
  Hazelcast 처럼 `isHeldByCurrentThread()` 를 던지고 남의 `unlock()` 에
  `IllegalMonitorStateException` 을 내는 것. 판별 단언은 `release()` 뒤 `!isLocked()` 다.
  고치기 전 코드는 뒤 가짜에서 그 단언에 걸린다.

### 이 바이트코드가 사용자의 질문에 답하는 것

- **"잠금을 쥔 채 노드가 죽으면?"** — 잠금은 `IMap.lock(key)` 이고 임대 시간이 없다.
  Hazelcast 3.12 문서는 멤버가 클러스터를 떠나면 그 멤버가 쥔 잠금을 전부 놓는다고 적고
  있다 → **죽은 노드의 잠금은 풀린다(문서상; 여기서 관찰은 못 했다).** 반대로 **살아 있는
  노드의 멈춘 스레드**가 쥔 잠금은 아무도 회수하지 않는다 — 그래서 `finally` 와
  `@PreDestroy` 가 방어선이다.
- **"앱을 껐다 켤 때 잠금이 남나?"** — docker 7.8.1 에서 실제로 했다. 스캔 도는 중
  UPM 으로 비활성화 → 워커가 다음 스토어 접근에서 던짐 → `save(FAILED)` 도 던짐(스토어
  없음) → `finally` 가 놓음 → 다시 활성화 → **10초 안에 스캔 202.** 자연히 풀린다. 다만
  **그 실행은 행을 하나도 남기지 못한다**(스토어가 이미 없다) — 화면은 IDLE 로 돌아오고
  중단된 스캔의 흔적은 로그에만 있다. 그 뒤 `@PreDestroy` 로 취소를 걸어 두었는데, 이것이
  더하는 것은 **덜 걷고 죽는 것**뿐이다 — 취소로 멈춰도 `save(CANCELLED)` 가 없는 스토어에
  던지므로 결국 같은 `catch (Throwable)` 로 끝난다. **이 경로가 실제로 도는 것은 관찰하지
  못했다**(위 실험은 애노테이션을 넣기 전에 했다).
- **"진행률·취소가 안 보이는 게 정말 그 모습인가?"** — `progress` 와 `cancelRequested` 는
  volatile 필드 둘이고 클러스터로 전파되는 곳이 없다. 코드로 확정이고 시험은 못 한다.

### 정직하게 남는 것

- Server 쪽 `ClusterLockService` 빈이 **무엇인지 못 찾았다.** `WEB-INF/lib` 의 어느 jar 에도
  `HazelcastClusterManager` 외의 구현체가 없다(번들 플러그인일 것이다). 아는 것은
  `isHeldByCurrentThread()` 가 답하고 스레드 사이 배타가 성립한다는 관찰뿐이다.
- 노드 두 대의 실제 경합과 죽은 노드의 잠금 회수는 **여전히 미검증**이다. 이번 결함은
  그 검증이 있었다면 첫 회에 잡혔을 것이다.

## 37. 정리가 요청 스레드에서 도는 것 — 앞단이 ALB 면 60초에 끊긴다

**날짜**: 2026-09-15. **버전**: 1.2.0 에서 고침.

### 무엇이 문제였나

1.1.0 의 `POST /cleanup` 은 요청 스레드에서 끝까지 돌았다. 실측 33번에서 첨부 1,020개에
107초였고, 상한 `MAX_IDS=5000` 이면 파일당 약 105ms 로 약 9분이다.

사용자가 운영 환경의 앞단을 확인해 주었다. **AWS ALB(내부용)** 이다 —
근거는 `Set-Cookie` 의 `AWSALBTG`·`AWSALBTGCORS`, protocol h2, Remote Address 10.x 대역.
기본 유휴 시간 초과는 60초다.

여기서 중요한 것은 **ALB 의 60초가 "유휴" 기준**이라는 점이다. 요청 전체 소요 시간이
아니라 연결에 데이터가 오가지 않는 구간을 잰다. 그런데 정리가 도는 동안 연결에는
아무것도 흐르지 않는다 — 응답 본문은 다 끝난 뒤에야 만들어진다. **그래서 107초짜리
정리는 60초에 끊긴다.**

끊긴 뒤가 더 나쁘다. **삭제는 서버에서 계속된다.** 무결성 자체는 무사하다 —
`AjActionLog` 는 다 남고 `markStale()` 도 돈다. 사라지는 것은 응답이고, 그 응답에 실려
있던 파일별 내역이 없으면 **화면이 표의 구버전 수치를 깎지 못한다.** 관리자가 보는 것은
통신 실패 한 줄뿐이다.

### 왜 상한을 낮추지 않았나

500 으로 낮추면 약 53초, 300 이면 약 32초다. 두 가지 이유로 답이 아니다.

- **구멍을 좁힐 뿐 닫지 못한다.** 파일이 크거나 DB 가 느리면 300개도 60초를 넘는다.
  그리고 앱이 **인프라 설정값에 의존**하게 된다 — 담당자가 ALB 유휴 시간을 바꾸면 앱이
  조용히 깨진다.
- **대량이 이 기능의 값어치다.** 2,000개를 정리하려면 미리보기부터 일곱 번 반복해야 한다.

사용자 판단도 같았다(비동기 + 폴링). 든 이유 셋: 타임아웃 값에 의존하지 않는다,
브라우저를 닫아도 작업이 계속된다, 진행률을 보여줄 수 있다.

### 무엇을 했나

`CleanupRunner` 하나를 더했다. 구조는 `ScanService` 를 그대로 본떴고 실측 35·36 의 규칙을
똑같이 지킨다 — **잠금은 워커 스레드가 잡고**, **잠금을 잡은 뒤에만 진행률을 RUNNING 으로
세운다**.

- `POST /cleanup` 은 202 와 `batchId` 를 즉시 돌려준다.
- `GET /cleanup` 이 진행률이다. **표를 다시 보내지 않는 가벼운 응답**이다 — 8분짜리를
  1.5초마다 폴링하는데 매번 수천 행을 실을 수는 없다.
- `DELETE /cleanup` 이 취소다. **이미 지운 버전은 돌아오지 않는다.**

**미리보기도 함께 고쳤다.** `POST /cleanup/preview` 역시 요청 스레드에서 첨부마다
`getPreviousVersions()` 를 부르므로 약 14ms 씩(실측 4번) 든다 — 5,000개면 그것만으로
2분이 넘는다. 실행만 비동기로 바꾸면 미리보기가 같은 자리에서 끊긴다. 미리보기는 읽기만
하므로 **화면이 300개씩 끊어 순서대로 보낸다** — 잠금도 배치 정체성도 걸리지 않는다.

### 직접 밟은 자리 넷

1. **끝난 진행률과 결과를 따로 쓰면 안 된다.** 두 번의 쓰기 사이에 폴링이 도착한 화면은
   "끝났는데 파일별 내역이 없다"를 보고 표를 깎지 못한다 — 실측 34번이 그대로 돌아온다.
   `CleanupProgress.ended()` 가 **내역을 같은 스냅샷에 싣는다.**
2. **분모를 미리보기 뒤에 세우면 그동안 0/0 이다.** 시작할 때는 요청받은 개수로 두고,
   미리보기가 끝나면 **실제로 지울 것이 있는 파일 수**로 좁힌다. 좁히지 않으면 12개를
   다 지우고도 화면이 2% 에 앉아 있다.
3. **취소·실패에도 뒷정리가 돌아야 한다.** 취소한 실행에도 이미 지운 파일이 있다.
   `filesDone > 0` 이면 `markStale()` 을 부르고, 배치 요약 행은 **끝맺음을 가리지 않고**
   남긴다. 안 그러면 그 삭제는 아무도 한 적 없는 일이 된다.
4. **웹수도는 지우는 두 요청(`POST /cleanup` · `POST /cleanup/preview`)에만 건다.** 진행률
   조회 · 기록 조회 · 취소는 관리자 확인만 본다. 폴링(`GET`)은 웹수도를
   갱신하지 않으므로, 8분짜리가 도는 동안 확인 시간이 지나면 **관리자가 도는 삭제를 세울
   수 없게 된다.** 인증이 만료됐을 때 "계속 지운다"가 기본값이 되어서는 안 된다.

### docker 7.8.1 에서 실제로 돌려 본 것 (2026-09-15)

픽스처: `AJB` 의 `bulk-*.bin` 603개에 버전 3개씩(구버전 1,206개), `keep=1`.

| 시험 | 결과 |
|---|---|
| 미리보기 603개 (300개씩 끊어 2회) | **4.1초** |
| `POST /cleanup` 이 돌아오기까지 | **0.01초** (202 + `batchId`) |
| 정리 도는 중 `POST /scan` | **409** `busy` |
| 12초 시점 진행률 | `RUNNING 28/603`, percent 4 |
| `DELETE /cleanup` 뒤 | **`CANCELLED` 29/603 · 58버전 · percent −1** |
| 취소 뒤 `stale` | **true** |
| 취소 뒤 배치 기록 | **`CANCELLED` files=29 versions=58 spaces=AJB** |
| 남은 574개 완주 | **`DONE` 574/574 · 1,148버전 · 건너뜀 0 · 실패 0 · percent 100 · 120초** |

| `keepActionDays` 999999 → 저장 | **36500** (상한) |

**120초가 요점이다.** 옛 동기 방식이면 ALB 유휴 60초를 두 배로 넘겨 끊겼을 시간인데,
브라우저는 첫 0.01초에 답을 받고 나머지는 폴링으로 따라갔다.

**취소에 percent 가 −1 이다.** 100 이 아니다 — 끝난 것과 완주한 것은 다르다.

### 보관 정책 잘라내기 — 실제로 지워지는가

`ACTION_LOG` 1,395행과 `ACTION_BATCH` 8행을 Postgres 에서 400일 전으로 되돌린 뒤 정리를
한 번 돌렸다(지울 것이 없는 첨부 하나 — 삭제는 0이지만 뒷정리는 돈다).

| | 전 | 후 |
|---|---|---|
| `ACTION_LOG` 행 | 1,998 | **603** |
| `ACTION_BATCH` `RECONSTRUCTED` | 8 | **0** |

`AT < ?` 가 AO 의 인용을 거쳐 Postgres 에서 제대로 도는 것이 여기서 확인된다.

### 남는 한계

**1.2.0 은 7.12.3 에서 다시 돌려 보지 않았다.** 위 표는 전부 docker 7.8.1 × Postgres 다.
새로 쓴 호스트 API 는 없다 — `Thread` · `TransactionTemplate` · AO 는 이미 쓰던 것이고,
1.2.0 이 더한 것은 그 조합뿐이다. 그래서 위험은 낮다고 보지만 **확인한 것은 아니다.**

노드가 다르면 진행률도 취소도 안 보인다. `progress` 와 `cancelRequested` 가 volatile 필드
둘이고 전파되는 곳이 없다 — 스캔과 같은 한계이고 같은 이유로 안 고쳤다(실측 35번).

## 38. 정리 기록을 배치 단위로 — 그리고 1.1.0 기록을 잃지 않기

**날짜**: 2026-09-15. **버전**: 1.2.0.

### 무엇이 문제였나

실측 35번의 부수 관찰이다. 파일당 한 행 · 한 쪽 200행이라 **250파일 배치 하나가 이전
실행들을 화면 밖으로 밀어낸다.** 이 인스턴스에서 실제로 그랬다 — 뒤의 두 배치(250·120)가
`ACTION_LOG_PAGE` 를 채워 `/cleanup/log` 에 그것만 보였고, **첨부 1,020개를 지운 가장 큰
배치가 DB 에 있는데 보이지 않았다.**

### 사용자가 정한 것

배치 단위로 바꾸고, 기록이 무한정 자라지 않게 보관 기간을 둔다. 처음 제안은 7일이었는데
**되돌릴 수 없는 삭제의 유일한 흔적**이라는 점을 들어 다시 정했다 — **설정값, 기본 1년,
하한 30일**. 며칠짜리 창은 감사 기록이 아니라 최근 활동 목록이다.

### 무엇을 했나

- `AjActionBatch` 엔티티 하나. 실행마다 요약 한 행이다. **파일별 행은 그대로 둔다** —
  "어느 파일의 몇 번 버전이 사라졌나"가 그 표의 존재 이유다. 요약만 남기면 통계가 된다.
- `GET /cleanup/log` 는 기본이 배치 목록이고 `?batch=<id>` 가 그 실행의 파일별 내역이다.
- 보관은 `Settings.keepActionDays`(기본 365). **스케줄러를 쓰지 않는다** — 정리할 때마다
  지나간 것을 훑어 지운다. 정리를 안 하면 이 표는 자라지 않으므로 그것으로 충분하고,
  스케줄 작업을 붙이면 클러스터에서 어느 노드가 도는지를 새로 다뤄야 한다.

### 밟은 자리 둘

**1. `AT` 는 따옴표 없이는 Postgres 에서 조회되지 않는다.** AO 가 만든 칼럼이 대문자
`AT` 인데 따옴표 없는 `AT` 는 소문자로 접혀 `column "at" does not exist` 다. 직접 확인했다.

그런데 AO 가 대신 인용해 준다. `DatabaseProvider.processWhereClause()` 가
`SqlUtils.processWhereClause()` 로 넘기고, 그 정규식이
`(\w+)(?=\s*((=|!=|>|<|...)(\s|\()))` 라 **연산자 뒤에 공백이나 여는 괄호가 있어야**
식별자로 본다. `"AT < ?"` 는 걸리고 `"AT<?"` 는 안 걸린다. **조건절에서 연산자 양옆
공백을 지우지 말 것.**

**2. 1.1.0 기록에는 요약 행이 없다.** 그대로 두면 업그레이드하는 순간 이전 실행이
목록에서 통째로 사라진다 — DB 에는 있는데 보이지 않는 것이 가장 나쁜 쪽이다.
`ScanStore.backfillBatches()` 가 파일별 행을 배치별로 묶어 요약을 만든다. JVM 이 뜬 뒤
`/cleanup/log` 첫 호출에서 한 번 돈다.

**끝맺음은 `RECONSTRUCTED` 로 적는다.** 파일별 행만으로는 그 실행이 끝까지 갔는지 도중에
멈췄는지 알 수 없다. 모르는 것을 `DONE` 이라고 적으면 기록이 아니라 추측이다.

docker 7.8.1 에서 확인했다: 1.1.0 → 1.2.0 업그레이드 뒤 **배치 8개가 전부 복원**됐고,
그중에는 전에 화면에서 밀려 있던 1,020파일 배치가 들어 있다. AO 가 기존 표를 고쳐
`AT` 인덱스를 만드는 것도 함께 확인했다(`index_ao_13c16c_action_log_at`).

### 하지 않은 것

**"일 단위로 나눠 저장"은 불가능하다.** AO 에는 테이블 분할이 없다. 날짜로 묶는 것은
받는 쪽 몫으로 두었다 — `at` 이 ISO 시각이고, 서버가 `yyyy-MM-dd` 를 만들면 어느
시간대인지를 새로 정해야 한다.

**기록 화면은 만들지 않았다.** `/cleanup/log` 는 지금도 REST 뿐이다. 화면을 더할지는
사용자와 따로 정할 일이다.

## 40. 진행 막대가 안 보였다 · 랭킹과 중복에도 쪽을 붙였다

**날짜**: 2026-09-15. **버전**: 1.2.0.

### 진행 표시가 안 보인다는 제보

사용자가 브라우저에서 정리를 돌렸는데 단추 옆 진행 표시를 보지 못했다. 재현해서
화면이 무엇을 언제 그리는지 그대로 따라가 봤다(첨부 13개, `keep=1`).

| 시각 | 화면 |
|---|---|
| 0.00초 | "구버전을 삭제하는 중..." |
| 0.01초 | 202 도착 → "삭제 중... **0/13개**" |
| 1.52초 | 1차 폴링 → 이미 `DONE` → "파일 13개에서 구버전 39개 삭제" |

**고장이 아니었다.** 다만 첫 폴링을 1.5초 뒤에 하는 바람에 **짧은 작업은 "0/13개" 하나만
보여 주고 끝난다.** 숫자가 한 번도 안 움직이니 아무 일도 없었던 것처럼 보인다.

고친 것 둘:

- **첫 폴링만 350ms 로 당겼다.** 그 뒤로는 1.5초 그대로다. 짧은 작업에서도 숫자가 최소
  한 번은 움직인다.
- **진짜 막대를 그린다.** 전에는 글자 한 줄뿐이었다. 스캔이 쓰는 `.aj-progress` 를 정리
  줄에서 그대로 쓴다 — 총계를 모르는 동안에는 비율을 지어내지 않고 흐르는 줄무늬를
  쓰는 규칙까지 같다. **글자보다 막대가 먼저 눈에 들어온다**는 것이 이 제보의 요지다.

### 랭킹·중복 화면에도 쪽을 붙였다

사용자 지적: 실제 인스턴스에서는 스페이스 랭킹과 중복 목록도 수천 줄이 된다. 상세
화면에만 쪽이 있었다.

세 화면이 같은 것을 쓰도록 공용으로 뺐다 — `rerender()` · `bindPageLinks()` · `slice()`.
화면마다 따로 적으면 한쪽만 고치는 사고가 나고, 이번이 바로 그 경우였다.
랭킹 화면에는 거를 것이 없으므로 "쪽당 건수" 하나만 두는 `renderPerPage()` 를 쓴다
(서블릿의 `aj-filters` 칸을 랭킹 화면에도 내보내게 고쳤다).

**막대 기준을 자르기 전에 잰다.** 이게 이번에 새로 생긴 유일한 위험이다. 쪽 안에서 다시
재면 쪽을 넘길 때마다 같은 스페이스의 막대 길이가 달라지고, "가장 큰 스페이스 기준"이라는
범례가 거짓이 된다.

### 브라우저 없이 화면 코드를 돌려 보는 법

여기에는 브라우저가 없어서 화면 코드를 두 번이나 확인 못 한 채 넘겼다. Nashorn(JDK 8 의
`jjs`)에 최소 DOM 을 물려 **IIFE 를 실제로 실행**하면 문법이 아니라 **배선**을 본다 —
없는 함수를 부르거나 없는 칸에 쓰면 거기서 터진다.

| 시험 | 결과 |
|---|---|
| 랭킹 6건 | 줄 6 · 쪽 이동줄 있음 · 쪽 번호 없음(1쪽) |
| 랭킹 137건 | 줄 **50** · 쪽 번호 링크 2개(총 3쪽) |
| 중복 3건 | 줄 3 · 쪽 번호 없음 |
| 중복 220건 | 줄 **50** · 쪽 번호 링크 3개(총 5쪽, 생략 표시 포함) |
| 가장 큰 스페이스를 마지막 쪽에 두고 1쪽 막대 | **1%** (쪽 안에서 쟀다면 100%) |

**이 방식을 다음에도 쓸 것.** 하네스는 저장소에 없고 시험용 임시 파일이었다 — 다시
필요하면 이 항목의 설명대로 만들면 된다: `document`·`window`·`XMLHttpRequest` 를
객체 몇 개로 흉내 내고, `aj-app` 에 `data-screen` 을 붙여 화면을 고르고, XHR 이 준비한
payload 를 돌려주게 하면 된다.

**한계**: DOM 흉내지 브라우저가 아니다. 눈에 보이는 모양·CSS·실제 클릭은 여전히 사람이
봐야 한다. 이 하네스가 잡는 것은 "코드가 도는가"까지다.

### 확인

REST 로 여섯 가지를 실제로 봤다(docker 7.8.1):

| 시험 | 결과 |
|---|---|
| 보고 응답의 `cleanup.done` | **빈 배열** |
| 도는 중 남의 배치로 `DELETE /cleanup?batch=` | `cancelled=false`, 계속 돎 |
| 도는 중 `GET /cleanup/log` | 도는 배치의 요약 **0건** (잠금이 백필을 건너뜀) |
| 내 배치로 취소 | `cancelled=true` → `CANCELLED`, `GET /cleanup` 에 내역 12건 |
| 목록 정렬 | 맨 위가 방금 것(`AT DESC`) |
| 574개 배치 상세 | `total=574`, `actions=574` (전에는 200) |

**백필 쓰기 경로도 실제로 돌렸다.** 위 시험에서는 요약이 다 있어 `saveBatch` 가 한 번도 안
불렸다(어드바이저 지적). 574개 배치의 요약 행을 psql 로 지우고 재배포한 뒤 `/cleanup/log` 를
부르자 `RECONSTRUCTED · 574/0/0 · 1,148버전 · 587,776바이트 · AJB` 로 복원됐다 — 원본과
자리까지 같다. `?batch=` 도 `total=574, actions=574`.

**화면 쪽은 절반만 봤다.** Nashorn DOM 하네스는 payload 를 받아 표를 그리는 길만 돈다 —
`addEventListener` 가 빈 함수라 클릭 경로는 한 줄도 안 돈다. 그래서 10번(빈 랭킹의 필터 칸
비움)은 하네스로 확인했지만, **3·4·5·6 의 JS 는 문법 검사까지만이다.** 눌러 봐야 할 것:
5,000개 넘게 고르고 미리보기 → 상한 안내 · 미리보기 도는 중 유지 개수 바꾸기 → 버림 안내 ·
도는 중 중지 · 도는 중 네트워크 끊기 → 조작 복구와 5초 뒤 재부착.

**잠금을 쥔 백필의 부작용 하나.** JVM 이 뜬 뒤 첫 `/cleanup/log` 조회가 백필을 도는 몇 초
동안 `POST /scan` · `POST /cleanup` 은 409 "다른 작업이 돌고 있다"를 받는다. 일시적이고
올바른 거절이지만 그 순간의 문구는 "무엇이" 도는지를 말하지 않는다 — 409 에 원인을 적지
않는 기존 규칙 그대로다.

### 리뷰가 가르친 것

- **"뒷정리"도 실패한다.** 끝 스냅샷처럼 반드시 써야 하는 것은 `finally` 에 둔다.
  `catch (Throwable)` 을 한 번 통과했다고 그 뒤가 안전한 것이 아니다.
- **"요약이 없는 배치"는 두 종류다** — 옛것과 도는 것. 구별할 수 없으면 도는 것이 없는
  순간을 만들어야 하고, 그 순간은 잠금이 만든다.
- **주석이 코드와 다르면 다음 사람이 주석을 따른다.** 웹수도 문장을 그대로 따랐다면
  1.5초 폴링에 웹수도가 걸려 실측 3번의 함정으로 되돌아갔을 것이다.

### H2 에서의 보관 잘라내기 — 여기가 진짜 미확인이었던 곳

실측 38 에서 `AT` 조건절을 Postgres 로만 봤다. H2 는 다른 방언이라 따로 본다.

AO 가 만든 인덱스가 H2 에도 있다: `INDEX_AO_13C16C_ACTION_LOG_AT` ·
`INDEX_AO_13C16C_ACT863779389` (ACTION_BATCH 의 `AT`).

H2 파일은 도는 Confluence 가 잠그고 있어 **사본을 떠서** 같은 문장을 돌렸다
(`h2-1.4.200.jar` 의 `org.h2.tools.Shell`).

| 시험 | 결과 |
|---|---|
| 따옴표 **없는** `AT < ...` | **동작한다**(63) — Postgres 에서는 `column "at" does not exist` 였다 |
| 따옴표 붙은 `"AT" < ...` | 동작한다(63) |
| 30행을 400일 전으로 → `DELETE ... WHERE "AT" < 365일전` | **정확히 30행 삭제**, 63 → 33 |
